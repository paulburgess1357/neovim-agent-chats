INTRODUCTION                                        *agent-chats-introduction*

Neovim Agent Chats lists every chat of Claude Code, Codex, Qwen Code and
opencode in one place, shows which need you, and lets you go into, search
and start chats from Neovim.

It reads what the agents already write to disk and listens to what they
report through their own hooks. It does not wrap how they are started, so
chats started anywhere are listed. It needs Neovim 0.11 or newer and nothing
else; a POSIX `sh`, `git`, `rg` and the system SQLite library are used when
present.

==============================================================================
SETUP                                                      *agent-chats-setup*
>lua
    require('agent-chats').setup()
<
`setup()` is optional. With it the plugin watches in the background from the
start, which drives notifications and the statusline segment. Without it
|:Chats| still works, and the watching begins the first time the board is
opened or the statusline function is called. Nothing is mapped globally; see |agent-chats-commands|
for `<Plug>` mappings.

Then, once: >vim
    :Chats hooks install
<
so that each agent reports its own status (|agent-chats-hooks|). The board
works without it, but for every agent except Claude Code "needs you" is then
a guess.

THE BOARD                                                  *agent-chats-board*

|:Chats| opens the board in its own tab: the list on the left, a pane on the
right. Asked for again from anywhere, it comes to the front, and `q` on it
leads back to where it was last asked for. The pane follows the cursor. For a
chat running in a terminal of this Neovim it shows that live terminal; for any
other chat it shows a summary: what state it is in and what it wants from you,
the folder it works in, your first prompt, your last prompt and the last
reply.

The row of the chat that is in the pane is marked in the list: a bar at its
left edge (`icons.shown`), and the line set off (|agent-chats-options|,
highlights). The mark stays when the cursor goes into the pane, so a glance
at the list says which chat you are in.

A terminal is shown in one window, not two. If a chat's terminal is on screen
already in a window of your own (the agent was started by hand in a terminal
in another tab, say), it stays there: the pane has the summary, which says
where the terminal is, and <CR> goes to it. Out of sight, it is shown live in
the pane like any other.

The bar above the list is the one place that names keys. At its left is what
<CR> does with the row under the cursor; every other key is at its right:
those of the row ("C Conversation", "A Archive"), then those of the list
("+ New Chat", "S Search", "R Refresh"), which stay where they are as the
cursor moves, and last the way to the menu. "C Conversation" is there for
every chat, also for one that <CR> can do no more than read. Where there is
room, the bar says behind <CR> why it only reads a chat ("it runs outside this
Neovim", "its folder is gone"; with less room "runs elsewhere", "folder
gone"). On a narrow list the keys give way one by one: "R Refresh" first, then
"A Archive" and "C Conversation" (they are in the menu), then the search and
the new chat; what <CR> does and the menu stay the longest. With the cursor in
the pane (a chat, a conversation) the bar names the keys of that view instead,
the way back first of all. The first line of the list counts the chats.

Marks on a row: `»2` two replies wait to be sent to the chat, `↗` it runs
outside this Neovim, `✎` a note of yours. What the note says follows its mark
as far as there is room (on a narrow list the mark stands alone; the summary
has the note in full).

`?` opens the menu: everything else that can be done, in words. It is one
list, all of it in view (on a screen too short for it, it scrolls, and its
footer says which way there is more), in parts with a heading each: the chat under the
cursor, your own marks on it (a name, a pin, a group, labels, a note), the
list (a new chat, the search, how it is grouped) and the board (the pane, the
status hooks, notifications). Move to a line and press <CR>, or click it. A
line that has a key shows it, and the key works there too: a key of the board
does in the menu what it does on the list, also when the menu does not list it
for this row (it then says why not, as on the list). For a letter either case
will do, unless the other case is a key of yours or of another action. (`q`
and <Esc> close the menu, so an action whose key is one of those has the key
after its words: "Close the board (q)" is what `q` does on the list.) Nothing
has to be remembered.

<CR> goes into the chat, to type: that is how a reply is written. One
running in this Neovim is focused; one that
ended is resumed in its own folder (the summary says which); one that runs
somewhere else can only be read here, so its conversation opens.

The first time the board opens, the pane introduces it (`board.intro`).

KEYS, AND YOUR OWN                                          *agent-chats-keys*

The board's own letters are capitals, so every lowercase key stays what it
is everywhere else. The cursor passes over the lines that stand for nothing
(the counts at the top, the gap between two groups): `gg` lands on the first
heading and `G` on the last row.

    <CR>        Go into the chat and type. On a heading: fold or unfold the
                group
    C           Read the whole conversation, tool calls folded
    +           New chat: pick the agent, and it opens
    S  or  /    Search every chat, inside the conversations too
    R           Refresh: look for changes now (the list also does so by
                itself)
    A           Archive the chat: it goes under "Archived", at the very end
                of the list. On an archived chat: take it out again
    ?  or  g?   The menu: everything else, for this row and for the board
    q           Back: out of a conversation, a search, the board
    <Esc>       End a search
    <Tab>       Fold a group, or show a chat's subagents

A double click opens a chat and a right click opens the menu.

In a conversation the bar above the list names the keys of the conversation,
and the same keys act on the chat being read: `q` goes back to the list, `+` and `S` start a chat and search as on the list, and `?`
opens the menu for that chat, with the keys that work there. `]]` and `[[`
(or `J` and `K`) move between your prompts. A tool call is folded to one
line, which says how much it holds and how to open it: <Tab> or <CR> on that
line, or the usual fold commands. `/` is Vim's own search there, with `n`
and `N` behind it: a long conversation is searched like any buffer, and the
search over every chat is on `S`.

Those are all the keys there are. The rest is in the menu, and has no key
until you give it one in `keys`:

    For the chat            queue (a reply for when it finishes its turn),
                            diff
    To keep track of it     rename, pin, move (into a group of your own, or
                            out of it), label, note, unread, yank
    For the list            group, show_all, read_all
    For the board           pane, hooks, notify

Two more can be given keys and are not in the menu, because they only move
what you see: scroll_down and scroll_up scroll the pane from the list.

`q` is the one way back, everywhere. So is closing the window, however that
is done: `:q` in a conversation goes back to the list just as `q` does. If
the cursor ends up in the summary (a window command, a click), the keys of
the list work there too, on the chat it shows, and `q` goes back to the
list.

In the floating layout the list and the pane are two floats, which Neovim's
window commands know nothing of: on the board `<C-w>h`, `<C-w>l`, `<C-w>w` and
`<C-w>p` move between the two as between two windows side by side. A key of
your own that calls `:wincmd` leaves the floats for the window behind them,
and that closes the floating board.

                                                     *agent-chats-your-keys*
Every key the board maps is local to its own windows, but a local mapping
still hides a global one. So:

- A default key is not bound where you have a mapping of your own on it.
  If `S` is yours, the board searches with `/`; if `?` is yours, the menu
  is on `g?`. The bar and the menu name the key that is bound, never one
  that is not.
- A key you name in the `keys` option is always bound: >lua
    keys = { back = 'q' }
< It is also that action's alone: an action that only had the key by
  default loses it (`keys = { archive = 'C' }` leaves reading the
  conversation without a key), and of two actions you give the same key the
  first in the alphabet keeps it. You are told of both; `<cr>` and `<CR>`
  are one key.
- An action left without a key is still in the menu and in `:Chats menu`.
  The menu marks a key that was left to you with `*`, and
  `:checkhealth agent-chats` lists every such key and what does its work
  instead.

This holds on the list, in a conversation and in a chat's terminal. The
keys are worked out when the board opens and again each time the list gets
the cursor, and a default key that a mapping of yours has turned up on
since (a plugin that loads late) gives way at the first press: your mapping
runs, and the bar stops naming the key. `setup()` called again takes effect
on the list and the summary at once; a conversation or a chat's terminal
that is already open keeps the keys it was opened with, and names those.

Neovim's own default mappings, and a key you mapped to <Nop>, do not count
as yours. A longer mapping of yours that merely begins with one of these
keys is not counted either: on the board the short key acts at once,
without waiting for more, so the longer one is out of reach there when
typed by hand.

The pop-up boxes (a reply to be queued, the menu) are the plugin's own
windows, open only until you send or close them, and their keys are fixed: the
footer of each names them.

GROUPS OF YOUR OWN                                        *agent-chats-groups*

The list is grouped by what each chat is doing. A chat can be taken out of
that and put in a group you name: "Put it in a group of your own" in the menu
asks which one (the groups there are, or a new one; the first time, only the
name). >

    ▾ Release  2   ●1
     ●  Claude  Review the release checklist ↗    plan            2m
     ·  Codex   Explain the borrow checker error  engine          2h

    ▾ Working  1   in the middle of a turn
     ◐  Codex   Add a picker for tab pages ↗      nvim-config     1m
<
Your groups are headings of their own above the others, by name. A chat stays
in its group whatever it does: its mark still says whether it needs you, is
working or has ended, and what needs you comes first in the group. The heading
says how many of its chats want a look, also while it is folded, and the
counts on the first line include them. A chat in a group is not dropped from
the list for being old (`board.max_age_days`), and neither is one you pinned.

"Move it out of ..., or to another group" on a chat that is in one offers the
other groups, a new one, and "No group": it is then back where its status puts
it. A group is nothing but its chats: it is made by naming it, and it is gone
when the last chat has left it. The menu on the heading of a group of yours
has two lines for the group as a whole: "Rename this group", and "Take every
chat out of it (the group is gone then)", which asks first.

A search finds a chat by the name of its group, and its summary shows it
("Group   Release"). Your groups belong to the grouping by status: grouped by
folder, agent or worktree, the list shows those and nothing else, and you are
told so when you move a chat there.

FILTERING FOLDERS OUT                                     *agent-chats-filter*

Chats you do not want among the others (the ones a test suite starts, a
scratch folder) are filtered out by their folder, in the options: >lua

    require('agent-chats').setup({
      filter_out = { 'waffle', '~/tmp/scratch' },
    })
<
A name stands for every folder called that, wherever it is, and for what is
inside it; a path stands for that one folder and what is inside it. The chats
of those folders are under a heading of their own at the end of the list,
folded, however the list is grouped: >

    ▸ Filtered out  12   folders named in filter_out
<
<CR> on the heading unfolds it, and it stays as you left it. Filtered out, a
chat asks for nothing: it is not in the counts on the first line or in the
statusline, you are not notified about it (the `User` events are raised all
the same), and `:Chats next` does not go to it. It can still be opened, read
and searched for like any other, and its summary says why it is where it is.
A chat is there for as long as its folder is in `filter_out`, also one you
put in a group of your own.

                                                         *agent-chats-archive*
Archiving. `A` on a chat puts it away: it is listed under "Archived", a
heading at the very end of the list, after everything else and however the
list is grouped, folded until you unfold it. Archived chats are left out of
the counts on the first line and in the statusline. `A` on an archived chat
takes it out again, and it is back where it was (in its group of your own, if
it was in one). A chat that moves again (a new turn) comes back by itself. A
search still finds archived chats. The bar names the key as "Archive" or
"Unarchive", and the menu has the same line.

SEARCHING, REPLYING, STARTING CHATS                          *agent-chats-use*

Searching. There is one search. `S` asks for the text and narrows the list
while you type, from what each row shows and holds (names, folders, branches,
agents, what each chat is doing, labels, notes, your groups, your first and
last prompt, the last reply). When you pause
(`search.live`), and when you press <CR>, the conversations themselves are
read for the same text and the passages found are listed under their chats;
<CR> on a passage opens the conversation there, and `C` on the chat's own row
opens it at the first of them. What is read is what a conversation shows: your
prompts, the replies, and the line each tool call has ("Bash · make test");
what a call was given and what it returned as well with `search.tools`. Words
are looked for in any order in a row; inside conversations the text is looked
for as typed, ignoring case unless it has a capital. Archived chats are found
too; chats quiet for longer than `board.max_age_days` are searched only while
"Show older chats" is on (a search that finds nothing says how
many were not looked at). What was searched for is marked where a row shows it, so a chat found by
its folder shows why. While you type, the bar names the keys of the
prompt (<CR> keeps the search, <Esc> calls it off); afterwards `q` (or <Esc>)
ends the search, and `S` asks for another text (the prompt starts empty; <Up>
brings back the last one).

Replying. To reply, press <CR> and type: you are in the chat's own terminal,
with everything its agent offers. A chat that had ended is resumed first, in
its folder. There is no box to write a reply in, and no key for it.

A reply can also wait. The menu of a chat that is in the middle of a turn has
"Queue a reply for when it finishes its turn": it opens a box, and what is
written there is pasted into the chat's terminal when that turn ends. With
replies queued the row shows how many (»2), its summary shows them, and the
menu line reads "Queued replies (2): send, add or drop". (`keys.queue` gives
this a key. The key then works on any chat: on one that is not busy and has
nothing queued there is nothing to wait for, so it sends at once, and the
title of the box says which it will be.)

Nothing can be sent from here to a chat that runs outside this Neovim, or to
one whose folder is gone: no reply can be queued for such a chat, and replies
queued for it earlier can only be dropped. A reply sent to a chat
that has ended resumes it (`reply.ended`: in a terminal, or in the background,
where it runs with no terminal at all; while a background reply is being
answered the chat can be read and nothing else, and the board says so).

What is sent from the list (a queued reply, lines sent with `:Chats send`) is
pasted, never typed as keys, and Enter is pressed only once the terminal shows
the text (`reply.echo_wait`). An agent that is showing a dialog of its own
(trust this folder, update available, a permission prompt) does not take a
paste: then nothing is sent and you are told. A chat that shows as "Needs you"
is not pasted into at all: a queued reply waits until you have answered,
`:Chats send` tells you to answer first, and queued replies you send by hand
from the menu take you to the chat to answer.

A queued reply is only ever pasted into a terminal of this Neovim that still
has the chat in it, and never starts an agent by itself. If the chat ends
first its replies are kept, you are told, and from then on they go only when
you say so: "Queued replies" in the chat's menu sends them, adds to them, or
drops them. Opening the chat again does not send them. The summary of a chat
with replies queued says which of the two holds.

Nothing is pasted behind something you typed and have not sent: pasted behind
a half-written line, the two would go as one message. A queued reply waits
(you are told once) and goes when your line has been sent or cleared; lines
from `:Chats send` are not sent, and you are told why.

Nothing is typed into a terminal that the agent is not reading. An agent
started by hand in a shell and then suspended (CTRL-Z) has left the shell
reading, and what is pasted there would be run as commands: `:Chats send`
says so and sends nothing, and a queued reply stays queued.

What was written in the box and not sent (the box was closed, the chat did not
take it, the agent resumed for it exited at once, a background run failed) is
in the box again the next time, until Neovim is closed (a queued reply is kept
beyond that). What was written for a chat while its row was
still a stand-in for it, a draft or a queued reply, goes with the chat when
its agent has named it.

Notifications. When a chat needs you or finishes a turn, you are told
(|agent-chats-options|, `notify`). The menu switches all of it off and on
again: "Turn notifications off" is its last line but one, so from where the
menu opens `k` twice leads to it (the menu goes round), and <CR> switches.
That line always says which way the switch goes, so it tells you whether they
are on. It is one switch for every Neovim, and it is
kept when Neovim is closed. `:Chats notify`, `:Chats notify on` and `:Chats
notify off` do the same from anywhere, and `keys.notify` gives it a key. The
board itself goes on showing what needs you either way.

Starting a chat. `+` asks one thing: which agent. The question names the
folder the chat will start in (the one Neovim is in), and the agent used last
is its first line, so `+` and <CR> start another chat with it. The last line
leads to another folder: one used lately, a new git worktree of the repository
that folder is in (if it is in one), or any other. Then the agent's own
terminal opens and you are typing in it. What to say to it first, which model
it runs and everything else about it is chosen there, in the agent itself: the
board asks nothing more. `:Chats new claude` starts that agent without asking.
(What it is started with is `providers.<name>.cmd`.)

A new chat has a row from the start, so one always leads back to its terminal.
Until its agent has named it, the row says "(no prompt yet)". The cursor of
the list goes to the new row, so going back lands on the chat just started.

Folders. A chat belongs to the folder it was started in, and its agent is
always started there: when a chat that ended is opened, or sent a reply that
was queued. Neovim's own folder makes no difference, and neither does a `cd`
the agent did along the way. The folder is in the chat's summary, and on its
row when the list is wide enough. A chat whose folder no longer exists cannot
be resumed; it can still be read. Once it has ended and been read it is
listed under "Folder gone", a heading of its own at the end of the list that
is folded until you unfold it, so that "Ended" holds only chats that can be
taken up again. <CR> on such a chat reads it. When the folder is there again,
so is the chat among the others. (In a group of your own it stays where you
put it.)

A CHAT'S TERMINAL                                       *agent-chats-terminal*

While you type in a chat every plain key belongs to the agent. `<C-\><C-b>`
(`open.back_key`) goes back to the list; in the terminal's normal mode `q`
does. The pane is the chat's, every line of it: it has no title. Which chat
you are in is marked in the list (the bar at the left of its row), and for as
long as the cursor is in the chat the bar above the list names the key that
goes back in the mode you are in. Closing the window (`:q`) goes back as
well, and is what the bar names when no key is bound. A chat that is open
in a terminal here is listed as open ("Idle" or busier) from the moment its
terminal exists, never as "Ended".

`open.on_open` is called once for every terminal the plugin starts for a
chat, after the plugin has set its own keys, with the buffer and (when
known) the chat. What it maps is left alone. A terminal you made yourself (a
chat started by hand in a `:terminal`, or one from `open.where`) only gets
the key that goes back while typing. While it is on screen in a window of
yours the board leaves it there (|agent-chats-board|); out of sight, it is
shown in the pane.

The pane is the board's own window. A buffer the board shows there has not
been opened in a window of yours, so no |BufWinEnter|, |BufWinLeave| or
|BufHidden| is raised for it: an autocommand of yours that sets up, or
claims, whatever window a terminal turns up in is not run for the pane.

If your function maps a key of its own on top of one of the two that go
back, the bar stops naming that key: the plugin cannot know what yours
does. To have it named, return `{ back = 'q' }` for the key that goes back
in normal mode and `{ back_typing = '<C-x>' }` for the one while typing
(`require('agent-chats').open()` is what goes back). A key is named only if
something of yours is mapped on it there.

To have window keys that work while typing: >lua
    require('agent-chats').setup({
      open = {
        on_open = function(buf)
          for _, dir in ipairs({ 'h', 'j', 'k', 'l' }) do
            vim.keymap.set('t', '<C-' .. dir .. '>',
              [[<C-\><C-n><C-w>]] .. dir, { buffer = buf })
          end
        end,
      },
    })
<
                                                        *AgentChatsTerminal*
The same moment is the `User` event `AgentChatsTerminal`, with `data.buf`,
`data.key` and `data.chat` (the last two are nil for a chat that has only
just been started).

COMMANDS                                                *agent-chats-commands*

                                                           *:Chats* *:AgentChats*
:Chats                  Open the board, or go to it.
:Chats new [agent]      Start a new chat.
:Chats next             Go into the next chat that wants you, as <CR> would:
                        one that needs an answer first, else an unread one,
                        the longest-waiting first. Never one in a folder
                        that is filtered out (|agent-chats-filter|).
:Chats search [text]    Search every chat; asks for the text when none is
                        given.
:Chats menu             The menu for the chat under the cursor on the board.
:Chats notify [on|off]  Switch notifications on or off; alone, the other way
                        round.
:[range]Chats send      Send the lines, with file name and line range, to a
                        chat running in this Neovim. With text after it
                        (`:Chats send run the tests`), that text is sent
                        instead.
:Chats hooks            Overview of the status hooks, with keys to install
                        and remove them.
:Chats hooks install [agent ...]
                        Install hooks for the agents named, or for every
                        agent in use. Shows the changes and asks first.
:Chats hooks uninstall [agent ...]
                        Remove them again.
:Chats hooks show [agent ...]
                        The steps to install them by hand.
:Chats hooks status     One line per agent.
:Chats refresh          Look for changes now.
:Chats close            Close the board.
:Chats toggle           Open the board; close it when the cursor is in its
                        list.
:Chats health           Run `:checkhealth agent-chats`.

`:AgentChats` is the same command under a second name. Where another plugin
already owns `:Chats`, that is the name this plugin's hints use, and what
`<Plug>(agent-chats-send)` runs.

Mappings to bind yourself:

    <Plug>(agent-chats)          Toggle the board
    <Plug>(agent-chats-next)     Next chat that needs you
    <Plug>(agent-chats-new)      New chat
    <Plug>(agent-chats-search)   Search chats
    <Plug>(agent-chats-send)     Send the selection to a chat (visual mode)

==============================================================================
STATUS HOOKS                                               *agent-chats-hooks*

Each agent has an official way to tell other programs what it is doing.
Claude Code, Qwen Code and Codex run a command on events such as "about to
ask for permission" and "turn finished"; opencode hands its events to a
plugin file. `:Chats hooks install` sets these up:

    Claude Code   `hooks` in ~/.claude/settings.json. Running sessions pick
                  them up at once.
    Qwen Code     `hooks` in ~/.qwen/settings.json. New sessions; or open
                  /hooks once in a running one.
    Codex         ~/.codex/hooks.json. Codex runs a hook only after you
                  trust it: it asks the next time it starts ("Hooks need
                  review"), or run /hooks.
    opencode      ~/.config/opencode/plugins/agent-chats.js. New sessions.

The installer shows a diff of every file it would touch and asks. It edits
the file as text, so key order, indentation, comments and your own hooks
stay as they were; it checks that the result parses, that nothing but its
own entries differs and that every comment is still there; and it first
keeps the old file beside the new one as
`<file>.agent-chats-backup-<date>-<time>.<n>` (the last three are kept).

It leaves a file alone, and says why, when the file is not valid JSON,
cannot be read, is read-only, or changed while the diff was on screen. A
symlinked settings file stays a symlink and is edited where it points; a
link to nothing is left alone. opencode's plugin file, when it is a link
you made, is never written through: uninstalling removes the link only.
With no agent named, only agents whose own folder exists are set up.
Uninstalling takes out what was put in.

The hook is one POSIX shell script, copied to
~/.local/share/agent-chats/agent-chats-hook.sh (`hooks.script`). It appends
one line per event to ~/.local/state/agent-chats/events/<agent>/<session>.log
(`hooks.dir`): the time, the event's name and, when present, the
notification type, the tool's name, the subagent id, why the session
started or ended, whether a tool stopped because you interrupted it, and the
agent's process id. Prompts, replies, commands and
tool output are never stored. The script prints nothing and always exits 0.
The installed command is >
    AGENT_CHATS_EVENTS_DIR=<folder> sh <script> <agent> 2>/dev/null || true
<so it cannot block or fail the agent, and it writes where this Neovim
reads whatever the agent's environment is. It works whether or not Neovim
is running.

Entries made by hand are recognised as long as the command runs
`agent-chats-hook.sh` with the agent's name, ends in `|| true`, and writes
to the folder this Neovim reads (without `AGENT_CHATS_EVENTS_DIR=` that is
~/.local/state/agent-chats/events, or under $XDG_STATE_HOME).
`:Chats hooks status` and `:checkhealth` say so when the two differ.

From a script, without the question: >lua
    require('agent-chats.hooks').install()          -- every agent in use
    require('agent-chats.hooks').install({ 'codex' })
    require('agent-chats.hooks').uninstall()
<
==============================================================================
STATUSES                                                  *agent-chats-status*

    Needs you       The agent is blocked on you (permission, a question)
    Working         The agent is mid-turn
    Unread          The turn finished and you have not looked since (its
                    terminal live in the pane beside the list is looking)
    Idle            Finished, seen, the agent is still open
    Ended           No process has the chat open; it can be resumed

Opening a chat, reading its conversation, or having its terminal in front of
you for a couple of seconds marks it read. A chat is not moved from under the
cursor for having been read: its mark changes where it is, and it goes to
"Idle" or "Ended" when the cursor leaves its row. ("Mark read" in the menu
moves it at once.)

What a chat is doing is known three ways, the most direct that has spoken
being believed: the agent's hooks (|agent-chats-hooks|); an interface of
the agent that can be asked; and files and processes (the transcript, a
session registry, the process table).

Without hooks, Claude Code's session registry makes "Needs you" exact. For
the other agents it is then a guess: a tool call with no result and nothing
written for `status.stall_after` seconds. A long-running command looks the
same, so those chats are marked with a question mark and raise no
notification unless `notify.inferred` is set.

What hooks do not say: that you answered a prompt (the next news is the
tool finishing; Claude Code's registry fills that gap, and for a chat in a
terminal of this Neovim typing into the terminal counts as the answer), and,
for Claude Code and Qwen Code, that you interrupted a turn (the transcript
says so, and wins when it shows the turn over after the hooks last spoke).

The summary says where a running chat's status comes from, and
`:checkhealth agent-chats` says it per agent.

`providers.<name>.cmd` is how the agent is started; add flags there rather
than relying on a shell alias. `headless_args` are added to background
replies, for example to choose a non-interactive permission mode.
`providers.opencode.config_dir` says where opencode keeps its config when
that is not ~/.config/opencode.

`hooks.enabled = false` ignores what installed hooks report. `hooks.dir` is
where they write: after changing it, install again (the status says
"outdated" until then). `hooks.script` is where an install keeps the script;
hooks that are installed go on running the copy they name for as long as it
is there, so to move it, uninstall and install again.
`hooks.remind = false` drops the board's line about agents that can only
guess.

`open.where` as a function receives `{ argv, cmdline, cwd, env, title,
chat }`, opens a terminal and returns its buffer. `open.on_open` is for
your own setup of a chat's terminal (|agent-chats-terminal|).

`notify.scope` limits notifications to chats under the working directory
("cwd") or to chats running in this Neovim ("hosted").

`filter_out` lists folders whose chats are kept apart, under "Filtered out"
at the end of the list: a name (every folder called that) or a path (that
one folder), each with what is inside it. See |agent-chats-filter|.

`search.live = false` reads the conversations only when <CR> is pressed,
not while the text is typed.

`keys` maps action names to a key, a list of keys, or false. A default
gives way to a mapping of yours on the same key; a key set here never does
(|agent-chats-your-keys|).

Options written for an earlier version are still read: `transcript` is
`conversation`, `group_by = 'provider'` is 'agent', and the key actions
transcript, filter, help and close are read, search, menu and back. A key
given for something that was taken out (reply, fork, pass) is left out, with
a message that says so.

Highlight groups start with `AgentChats` and link to standard groups. The row
of the chat that is in the pane is `AgentChatsShown` (linked to |hl-Visual|),
and the bar at its left `AgentChatsShownMark` (linked to |hl-Title|); the bar
itself is `icons.shown`, and '' leaves it out.

==============================================================================
ADDING AN AGENT                                        *agent-chats-providers*

An agent is a table with these fields, passed to `register()`:

    name, label     Short id and display name.
    home()          Where the agent keeps its data.
    available()     Whether there is anything to read.
    discover()      One `{ id, path?, mtime, size, data? }` per chat. Cheap:
                    no file is opened.
    parse(entry, prev)
                    Called when an entry's mtime or size changed. Returns
                    `{ title, first_prompt, last_prompt, last_reply, cwd,
                    branch, model, created, updated, turn, turn_at,
                    activity, pending_tool, asking, parent_id }`, where
                    `turn` is "working", "waiting", "done", "aborted" or
                    "unknown". Returns nil for a chat with no conversation.
    messages(chat, opts)
                    The conversation after `opts.cursor`, plus a new cursor
                    (nil when it cannot read incrementally), plus true when
                    it had to start again from the top. Raises an error when
                    the conversation cannot be read. Messages are
                    `{ role, text, name, summary, input, lang, error, id,
                    time }` with role "user", "assistant", "thinking",
                    "tool", "tool_result" or "system".
    resume_cmd(chat), new_cmd(opts)
                    Argument lists that resume a chat and start a new one.

Optional. The first three are the ways a chat's status can be known; supply
any of them:

    hooks           `{ events, process?, config? }`. `events` maps the
                    names of the agent's hook events to what they mean:
                    "working", "active", "waiting", "resolved", "done",
                    "idle", "aborted", "start" or "ended"; or to a function
                    of the event that returns one. The agent runs
                    scripts/agent-chats-hook.sh with its name, and JSON on
                    standard input or the event and session id as
                    arguments. `config()` says how `:Chats hooks install`
                    sets that up.
    query(chats)    `{ [id] = { pid, turn?, turn_at?, ... } }` from a CLI
                    or API of the agent. Called at most every
                    `query_interval` ms.
    live(chats, reported)
                    The same from files and processes, on every refresh.
    locate(id, live)
                    The entry of a running chat not yet discovered.
    subagents(chat) Chats spawned by a chat.
    grep(query)     Ids of chats that may contain the text, for agents with
                    no transcript file per chat.
    rev(id)         A value that changes when something about the chat
                    changed outside its transcript (a title kept elsewhere).
    check()         Extra lines for `:checkhealth`.
    headless_cmd(chat, prompt), resume_prompt_cmd(chat, prompt)
    exact           `live()` reports the turn state itself.
    preassign_id    `new_cmd` honours `opts.id`.

The annotated contract is in `lua/agent-chats/types.lua`,
`lua/agent-chats/providers/claude.lua` is the reference implementation, and
`examples/pal.lua` is a complete small provider.

==============================================================================
LIMITS                                                    *agent-chats-limits*

- A chat running outside this Neovim can be read but not typed into.
- The menu as it is now was driven for real with Claude Code only. Codex,
  Qwen Code and opencode were driven when a queued reply still had a key of
  its own; what sends a reply has not changed since.
- Background replies cannot answer permission prompts.
- Queued replies are pasted into a terminal of this Neovim, or not sent: a
  chat that ended keeps its queue until you send or drop it from its menu.
- A dialog an agent shows is only known when the agent reports it. For any
  other (an update offer, a trust question) a reply is not sent, because
  the pasted text does not appear; you are told to look.
- Codex and opencode keep no record of running sessions; which process has
  which chat open is matched from process inspection, and from the process
  a session's hook ran under once hooks are installed. (Codex 0.171 keeps a
  daemon, `codex app-server`, that holds every session and runs their
  hooks: it being alive is not taken for a chat being open.)
- Two opencode processes in one folder, without its hooks, can only be told
  apart by a guess. A process started with a prompt is matched to the chat
  that begins with that prompt; beyond that there is the folder and the time.
  The guess is still made, so that each row leads to a terminal, but nothing
  is typed on it: queueing a reply for such a chat says why, and the reply is
  written in its terminal. With the hooks installed, opencode says which
  process has which chat.
- A reply that resumes a chat is handed to its agent as an argument when it
  starts, and an argument can hold about 127 KB. A longer one is refused with
  that reason and kept.
- After you approve a prompt, no agent reports it; see |agent-chats-status|.
- Developed and tested on Linux. The path for systems without /proc is
  exercised by the tests but has not run on a Mac. Windows is untested and
  the shell hooks need a POSIX `sh`.
- The agents' file formats are not public interfaces and may change.
